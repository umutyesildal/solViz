SolViz Studio: Natural Language to Visualization for Solana Data

Architecture and Design Overview

SolViz Studio is envisioned as a web application that turns natural language questions about Solana into data visualizations. The architecture consists of several key components:

  • Front-End UI: A web interface (e.g. React) where users input queries in plain English and view resulting charts. It manages query input, displays charts, and provides options to refine, save, or export visualizations.
  • Backend Orchestrator: A server (e.g. Node/Express or Python/FastAPI) that coordinates between the LLM, data APIs, and visualization generator. This layer receives the user query, calls the LLM to translate it into a data query, fetches data from the appropriate Solana API, and then formats the result for visualization.
  • LLM Query Engine: An AI component (using GPT-4 or similar) that converts user natural language into a structured query (SQL, GraphQL, or RPC request) against Solana data sources. This engine uses carefully designed prompts (and possibly OpenAI function-calling) to ensure the output query matches the required syntax and schema.
  • Data Provider Connectors: Modules that interface with various Solana data APIs – for example, a GraphQL client for Bitquery, REST clients for Helius and Flipside, and an SQL client or API wrapper for Dune. Each connector handles authentication (API keys) and query execution, returning data in a normalized format.
  • Visualization Module: Logic that takes the returned data and automatically selects an appropriate chart type. It uses a visualization grammar (like Vega-Lite) to generate an interactive chart. This module also handles front-end rendering (perhaps via Vega-Lite JS libraries) and ensures charts are responsive and interactive.
  • State & Storage: A database or in-browser storage to cache schema metadata (for faster LLM prompts) and to save user-created charts or dashboards. Saved visualizations include the query, dataset, and chart specification so they can be reloaded or shared without re-computation.

Design Decisions: The system is modular: the LLM engine, data connectors, and visualization are decoupled. This allows swapping out the LLM or adding new data sources in the future. We use a stateless query generation approach – each query is processed independently by the LLM with relevant context (schemas, examples) provided in the prompt. Real-time updates (for live data queries) are handled via streaming APIs or periodic refresh in the front-end. The architecture favors a mix of real-time API calls (for current state queries) and warehouse queries (for historical analytics), since Solana data needs both low-latency and deep analytics capabilitieshelius.devhelius.dev.

Security and cost considerations are also important design factors:

  • The backend sanitizes and validates LLM-generated queries (to avoid malicious or overly expensive operations).
  • API keys for data providers are kept secure on the server side.
  • Rate limits and quotas for each provider are monitored; the orchestrator may fall back to an alternate provider if one’s quota is exhausted or if it better serves a particular query type (more on this in the data integration section).

Overall, the design emphasizes a seamless user experience: users ask questions in natural language and get charts with minimal delay. Under the hood, the system dynamically chooses the best data source and query plan, much like how a database optimizer works, but guided by an LLM for understanding the intent.

Multi-Provider Solana Data Integration

SolViz Studio integrates multiple Solana data APIs to leverage their unique strengths. The four main providers considered are Bitquery, Helius, Flipside Crypto, and Dune Analytics. Each offers different data access methods and coverage:

  • Bitquery – a GraphQL-based blockchain data service supporting Solana. Bitquery provides rich indexed data (transactions, token transfers, NFT metadata, staking events, etc.) via GraphQL queries. It even offers real-time WebSocket subscriptions for live data (e.g. new trades) and decoded instruction data for readabilitybitquery.iobitquery.io.
  • Helius – a Solana-focused API and RPC provider with enriched endpoints. Helius offers high-performance RPC nodes and specialized APIs for tokens and NFTs (the Digital Asset Standard API)helius.devhelius.dev, as well as enhanced transaction parsing. It excels at giving human-readable outputs for on-chain data (e.g. decoding program state, token metadata, NFT collections) and provides streaming via webhooks and WebSockets for real-time eventshelius.devhelius.dev.
  • Flipside Crypto – a data warehouse (Snowflake) with pre-indexed Solana datasets accessible via SQLhelius.dev. Flipside’s ShroomDK API allows queries against tables that include Solana transactions, token transfers, DeFi events, NFT sales, etc. This is ideal for historical analysis and heavy aggregations, since the data is organized in analytics-friendly tables (e.g. solana.core.fact_events, solana.nft.fact_nft_sales etc.)medium.commedium.com. Queries are not real-time (data lags ~15 minutes)helius.dev but Flipside offers generous free usage quotas (millions of query rows) making it suitable for community dashboards.
  • Dune Analytics – a community-driven analytics platform where users write SQL queries on curated Solana datasetshelius.dev. Dune provides raw tables (like solana.transactions, solana.instruction_calls, etc.) and higher-level abstractions. Dune’s API allows running saved queries or direct SQL against their engine, with a pay-per-use credit systemhelius.dev. Dune is powerful for complex queries and for leveraging community-built queries, though its API requires managing query execution ids and results asynchronously.

Integration Strategy: We incorporate all four providers behind a unified interface. The LLM can choose which provider (or combination) to use for a given user query, based on the data needed:

  • Simple account info or on-chain state: For questions about a specific address or transaction (e.g. “What is the balance of address X?” or “Decode this transaction signature”), the app favors Helius or Bitquery. Helius can directly fetch token balances or parse a transaction via its RPC or enhanced API (e.g. getBalance or getTransaction endpoints). The Solana ChatGPT plugin, for example, implemented endpoints like /getBalance and /getTransaction which internally call RPC and then format the responsegithub.comgithub.com. Bitquery can also get balances or transaction details via GraphQL, but using Helius/RPC is more direct for single-address queries.
  • NFT data: Helius and Bitquery both provide NFT-specific data. Helius’s DAS API can list all NFTs owned by a wallet or fetch NFT metadata by mint addresshelius.devhelius.dev. Bitquery’s Solana NFT API can retrieve NFT ownership, metadata, transfer history, and even marketplace tradesbitquery.iobitquery.io. For example, to get all NFTs in a wallet, the LLM might produce a Bitquery GraphQL query filtering balance updates for NFT mint addresses held by that owner. Alternatively, Helius offers a getAssetsByOwner method (via Metaplex’s API) to list NFTs, which was used in the Solana ChatGPT plugingithub.com. For NFT trading volume or top collections, Flipside or Dune can be used (they have tables like fact_nft_sales for Solana with price and marketplace datamedium.com). The strategy is to use Helius/Bitquery for item-level or live NFT info (e.g. “show my NFTs with images”) and Flipside/Dune for aggregated NFT stats (e.g. “daily NFT sales volume last month”).
  • Staking and validator data: Bitquery has a dedicated Staking/Rewards API that parses staking transactions and reward eventsbitquery.io. If a user asks “How much SOL is staked over time?” the LLM could use Bitquery’s Solana Rewards GraphQL to sum stake amounts by epoch. Flipside’s Solana tables also contain stake accounts and reward info (since Flipside’s analytics schema includes stake program interactions). In fact, complex stake metrics (like distribution of stake, top validators, stake activation over epochs) were built using Flipside in community dashboardsmedium.commedium.com. The integration will lean on Flipside for broad stake analytics (e.g. total staked SOL, historical trends per epoch) since it can do SQL aggregations easily, while Bitquery can handle specific queries like “what were the latest stake rewards to a given account?” via its GraphQL.
  • Transaction history & token transfers: This is a common query type (“Show SOL transfer count over time” or “Top 10 holders of token X”). Bitquery provides an easy GraphQL interface to token transfers and holders – e.g. a query to get the top 100 holders of a SPL token by filtering BalanceUpdates on that token mintdocs.bitquery.iodocs.bitquery.io. Bitquery’s advantage is it can give current state (like current holders) in one query, and even subscribe to changes. For historical daily transfer counts, Flipside or Dune are well-suited: e.g. Flipside’s solana.core.fact_events table can be filtered for transfer instructions and grouped by datemedium.commedium.com.
  • Mempool / real-time activity: Solana doesn’t have a traditional long-lived mempool (thanks to Gulf Stream), but near-real-time transaction flow can be tapped. For live metrics like “current TPS” or “recent transactions”, the app can use Helius or Bitquery streaming. Bitquery supports GraphQL subscriptions that push new transfers or trades instantlybitquery.io, and Helius offers WebSocket or webhook streams from their Geyser infrastructurehelius.devhelius.dev. The integration might maintain an open WebSocket (to Helius or Bitquery) that updates certain live dashboards (like a mempool activity feed or latest NFT mint ticker). For user queries specifically asking about unconfirmed activity, we’d rely on these streaming endpoints since Flipside/Dune only update with confirmed data after some delayhelius.dev.

API Endpoints & Examples: The following illustrates how queries are formed for each provider:

  • Bitquery GraphQL example: To get the token balances in a wallet, the LLM might produce a GraphQL query using Bitquery’s schema. For instance:
    graphql
Copy
query WalletTokenBalances {
  Solana {
    BalanceUpdates(
      where: {BalanceUpdate: {Account: {Owner: {is: "<WALLET_ADDRESS>"}}}}
      orderBy: {descendingByField: "BalanceUpdate_Balance_maximum"}
    ) {
      BalanceUpdate {
        Balance: PostBalance(maximum: Block_Slot)
        Currency {
          Name
          Symbol
        }
      }
    }
  }
}

    This GraphQL query (similar to Bitquery’s examples) filters balance updates by wallet address and returns the latest balance of each token and its symboldocs.bitquery.iodocs.bitquery.io. Bitquery’s endpoint is a single GraphQL URL (e.g. https://graphql.bitquery.io), so the app sends this query with an authorization token and gets JSON results.

  • Helius REST/RPC example: Suppose a user asks, “What tokens does wallet X hold and what are their USD values?” The LLM could decide to call Helius. The SolViz backend might use Helius’s REST API like: 

    GET https://api.helius.dev/v0/addresses/<WALLET_ADDRESS>/balances?api-key=YOUR_KEY

    This (hypothetical) endpoint would return all token balances for the address, including SOL and SPL tokens, with metadata. Helius’s documentation indicates their Token API can fetch token balances and even quote USD priceshelius.devhelius.dev. If Helius doesn’t have a single endpoint for all balances, the orchestrator could fall back to a standard RPC call getTokenAccountsByOwner and then use Helius’s price service (or HelloMoon API as used in Solana’s ChatGPT plugin) to convert to USDgithub.com. Another Helius example: for NFT data, one can call a JSON RPC on Helius with method getAsset or getAssetsByGroup (for collection)helius.dev, which returns structured NFT metadata that the LLM can parse and relay.

  • Flipside SQL example: For a question like “Daily number of transactions and users in the past month,” the LLM would generate an SQL query for Flipside. Using Flipside’s schema, an example (drawn from a Flipside tutorial) might be:
    sql
Copy
SELECT DATE_TRUNC('day', block_timestamp) AS date,
       COUNT(DISTINCT tx_id) AS tx_count,
       COUNT(DISTINCT signers[0]) AS user_count
FROM solana.core.fact_events
WHERE block_timestamp > CURRENT_DATE - INTERVAL '30 days'
  AND succeeded = TRUE
GROUP BY 1;

    This query uses the fact_events table which logs Solana transaction events, grouping by daymedium.com. The orchestrator would send this SQL to Flipside’s API endpoint (using the provided API key). Flipside’s API (ShroomDK) typically expects a POST with the SQL query and returns a JSON of results once the query executes. We may use their Python/JS SDK under the hood, e.g. flipside.query(sql) in Python which abstracts the polling for resultdocs.flipsidecrypto.xyzdocs.flipsidecrypto.xyz. The result is a JSON array of date, tx_count, user_count that our app can turn into a time-series chart.

  • Dune API example: If the LLM chooses Dune (perhaps because a very specific Dune-curated table or an existing saved query is relevant), the backend can run a saved query via Dune’s REST API. For instance, Dune has a table solana.nft.sales in its curated sets; a user asks “Weekly NFT sales per marketplace”. The LLM generates a SQL similar to Flipside’s but for Dune’s schema:
    sql
Copy
SELECT date_trunc('week', block_time) AS week, marketplace, COUNT(*) AS sales_count
FROM solana.core.fact_nft_sales
GROUP BY 1, 2

    To execute on Dune, we first create or identify a Dune query ID that contains this SQL. Then we call Dune’s execute endpoint:

    bash
Copy
POST https://api.dune.com/api/v1/query/<query_id>/execute
Headers: X-Dune-API-Key: <API_KEY>

    The response will give an execution_id and the query will run asynchronouslydocs.dune.comdocs.dune.com. Our backend will then call Dune’s result endpoint or use their Python SDK to retrieve the result when readydocs.dune.comdocs.dune.com. (We may also leverage Dune’s newer API that allows direct SQL submissions, if available, to avoid manual query creation.)

Choosing Provider by Query Type: The system uses simple rules (and prompt engineering for the LLM) to pick the best data source:

  • If the query is address-specific or real-time, prefer Helius or Bitquery (RPC or GraphQL) for immediate results.
  • If the query is analytical, historical, or heavy, prefer Flipside or Dune (SQL engines)helius.devhelius.dev.
  • If one provider lacks data for a query, try another. For example, a request for “Solana wallet with most NFT trades” might be easier on Dune (if someone created a NFT trade volume table) whereas Flipside would require joining multiple tables – the LLM might know from its instructions which source has a ready dataset.
  • Consider quota/latency: Flipside queries might return in a few seconds, whereas a similar Dune query could be faster or slower depending on workload. If a Flipside query is too large (approaching their free limit) the app could warn or switch to Dune if the user has Dune credits. Conversely, if the user has no Dune API key configured, we wouldn’t choose Dune.

We maintain fallback logic. For instance, if a Bitquery GraphQL query fails (due to rate limit or error), the orchestrator might attempt an equivalent using Helius or a direct RPC call (since many Bitquery queries can be replicated with raw RPC data, albeit with more code). Similarly, if Flipside’s API is slow or down, we can route to Dune (assuming the query can be translated to Dune’s schema). This dynamic switching ensures reliability and optimizes for speed and cost – using free quotas where possible and sharing load among providers.

LLM-Driven Query Engine Implementation

At the heart of SolViz Studio is the Large Language Model that interprets user questions and produces correct, efficient queries. Building this component involves prompt engineering, output structuring, and robust validation:

  • Prompting Strategy: We craft a system prompt that clearly instructs the model about its role (“You are a data assistant for Solana blockchain analytics...”) and provides context about the available data sources and schemas. The model needs to know which providers exist and the high-level structure of their data. For example, the prompt might include brief descriptions like: “Bitquery: GraphQL schema with BalanceUpdates, Transactions, etc. Flipside: SQL with tables like solana.core.fact_transactions, solana.nft.fact_nft_sales...”. We also feed the LLM a few examples of user queries and the desired output format (one example per provider). This one-shot or few-shot approach guides the model to follow our format.
  • Function Calling / Structured Output: To enforce that the LLM returns a machine-readable query (instead of a narrated answer), we use the OpenAI function-calling feature. We define a function, e.g. generate_data_query(provider, query_text), where provider is an enum ("Bitquery" | "Helius" | "Flipside" | "Dune") and query_text is a string containing the actual GraphQL or SQL to run. The model, upon understanding the user request, will choose the function and fill in these arguments. For instance, the model might respond with:
    json
Copy
{
  "function": "generate_data_query",
  "arguments": {
     "provider": "Flipside",
     "query_text": "SELECT ... (SQL query as above) ..."
   }
}

    By using a function call, we get a guaranteed JSON structure that our backend can easily parse and act on. This method was demonstrated in similar contexts (e.g. converting NL to SQL with function calls) and helps avoid the model returning extraneous textalex000kim.com. If not using OpenAI’s functions, an alternative is to ask the model to output YAML/JSON directly with fields for provider and query – but the function approach is cleaner and reduces formatting errors.

  • Dynamic Schema Provisioning: To help the LLM produce correct queries, we provide schema information. We cache the schema of each API upfront:
    • For Bitquery (GraphQL), we can introspect their API to get type definitions for relevant entities (accounts, transactions, etc.). We’ll condense this into a prompt-friendly form (e.g. list of important query fields and filters). For example: “Bitquery Schema Snippet: BalanceUpdates has fields: PostBalance, Account.Owner, Currency.MintAddress, etc.”.
    • For Helius, since it’s mostly fixed endpoints, we simply describe what each endpoint returns (the model doesn’t need to output the exact REST call, since we handle it, but it should know what’s available; e.g. “Helius getNFTs returns all NFTs for owner”).
    • For Flipside and Dune, which have many tables, we can’t send everything. Instead, we maintain a mapping of concepts to tables. Using an embedding-based approach, we can store table schemas in a vector index and retrieve the ones relevant to the query. For example, if the user asks about NFTs, we inject schema info for fact_nft_mints and fact_nft_sales. (Uber’s internal “QueryGPT” system does something similar: it uses a vector database to fetch relevant table schemas and example queries based on the NL questionuber.comuber.com.) This way the prompt remains concise and focused on the domain needed.
  • Prompt Adaptation per Provider: We tailor the prompt depending on which provider the LLM is likely to use. If we have function calling, one approach is to present multiple function options (one for each provider) and let the model choose. Another approach is a two-step prompt: first, ask the model (with a smaller prompt) to decide which provider is best for the query (perhaps by having it output just the provider name). Then, in a second call, use a provider-specific prompt template that includes detailed schema for that provider and ask for the query. However, the single-step function call is efficient if the model is well-instructed on all providers at once. We include different examples in the few-shot prompt for each style. For instance:
    • Example 1: User asks for a wallet’s NFTs → model outputs a Bitquery GraphQL example.
    • Example 2: User asks for historical transaction count → model outputs a Flipside SQL.
    • Example 3: User asks for latest token transfers → model outputs a Helius/RPC example.

    By seeing exemplars, the model can infer patterns. We explicitly mention to only use one provider per query to keep things simple initially (no joining data across APIs in one go, though the backend could do multiple calls if absolutely needed).

  • Guardrails and Validation: Once the LLM produces a query, the backend validates it before execution:
    • Syntax check: We run a quick syntax validation (e.g. parse the SQL or GraphQL). If it fails, we know the model output was malformed. In such cases, we can either ask the LLM again with more constraints or do a minor correction (like adding a missing bracket) if obvious.
    • Schema check: We verify that the fields used in the query actually exist. For SQL, we could pre-check the query against a known schema (e.g., no unknown table names). For GraphQL, the Bitquery API itself will error if a field is wrong, but catching it beforehand allows a second chance with the LLM by providing the error message.
    • Limit enforcement: To avoid huge data pulls, the system might automatically append a LIMIT 1000 to SQL queries if not present, or restrict time ranges. If the user asked for “all-time data”, the LLM should include a sensible date filter or aggregation; if it doesn’t, our guardrail might add a default filter (like last 1 year) or ask the model to refine the query. We also ensure no unsafe queries are generated (like ones that attempt to modify data, though our connections are read-only by nature).
    • Cost awareness: For Dune, since queries cost credits, we might estimate the result size by doing a smaller COUNT(*) query first via the LLM plan or by limiting the date range. Similarly for Flipside, although free, large queries take longer – if we detect a potentially long-running query, we could notify the user that it may take a bit of time or suggest refining it.
  • Guardrails in Natural Language Understanding: We also add prompt instructions to avoid certain pitfalls: for example, if the user query is ambiguous or likely to produce a very expensive result (“show all transactions ever”), the LLM should politely request clarification or add reasonable limits. The prompt might say: “If the user request is too broad (e.g. no timeframe on a huge metric), assume a default recent timeframe or ask a follow-up (we can implement a clarifying question to the user if needed).” This ensures the model doesn’t naively generate a massive query that times out.
  • Step-by-step refinement: In complex cases, the system could do multi-turn interactions with the LLM. For instance, model first retrieves relevant schema (as in function-calling approach #2 from Alex Kim’s experiment)alex000kim.com, then uses it to produce the final query. We might implement this if single-shot performance is lacking. Initially, we try to keep it one-shot with all necessary context provided, which several text-to-SQL studies have shown to work for moderate schema sizesalex000kim.com.
  • Model Fine-tuning: For even better accuracy in the Solana context, we can consider fine-tuning or custom training. We could gather a dataset of <user question, ideal query> pairs. Sources might include public Dune queries (paired with their titles/descriptions as a pseudo NL question) or Stack Exchange questions about Solana data. By fine-tuning GPT-3.5 or a smaller LLM on these, we’d get a specialized model that might perform faster (and cheaper) than calling GPT-4 each time. However, given GPT-4’s strong capabilities and our ability to supply context, fine-tuning is an optional enhancement. Another approach is using retrieval augmented generation: store Solana knowledge (like common addresses, program names, etc.) so the model has more context to avoid errors in interpretation (for example, knowing that “SOL” refers to the native token, or that “Candy Machine” is an NFT mint program, etc., which might influence the query structure).

In summary, the LLM engine translates human questions to data queries with a combination of careful prompting, function-driven output formatting, and backend checks. These guardrails and schema-awareness ensure we get correct and safe queries that we can then execute to fetch the data.

Visualization and Charting Logic

Once we have the data results, SolViz Studio automatically generates an appropriate visualization. The goals for the visualization module are to choose the right chart type for the data, render it in an interactive way, and allow user-friendly interactions (tooltips, filters, etc.), all while maintaining a responsive layout.

  • Automatic Chart Type Selection: The system infers the best chart based on the structure of the query results:
    • If the result has a time series (e.g. a date column and a value column), a line chart is typically used to show trends over time. Multiple value columns or categories with a date would result in a multi-line chart (or area chart) with a legend.
    • If the data is an aggregation by category (e.g. top 10 tokens by volume), a bar chart or column chart is appropriate. For a small number of categories, a pie or donut chart could be considered (though pie charts are harder to read for many slices).
    • A single numeric value (like “current total staked SOL”) might just be shown as a KPI card or a big number, possibly with a gauge or indicator if there’s a target.
    • If data has geographical context (less likely in Solana’s on-chain data, unless analyzing IPs or something off-chain), we could do a map – but such cases are rare here.
    • For relationships or distributions (e.g. a scatter plot of two variables, or histogram of transaction sizes), the engine would choose those specialized charts when relevant.

    The chart selection can be rule-based. We implement a simple heuristic: examine the number of columns and their data types in the result. For example:

    • 2 columns: one time/datetime, one numeric → line chart.
    • 2 columns: one categorical, one numeric → bar chart.
    • 3 columns: time, category, numeric → line chart with series (category as series) or perhaps grouped bar by time.
    • 1 column: just numeric → big number display.
    • 2+ numeric columns with no obvious category → table or correlation plot.

    In addition, we could incorporate an LLM here as well – e.g., feed the data summary to a prompt: “Suggest a good chart type for this data.” But that may be overkill; a deterministic approach based on known best practices is sufficient for now.

  • Vega-Lite for Rendering: We choose Vega-Lite as the visualization framework. Vega-Lite is a high-level grammar of interactive graphics that can declaratively specify charts in JSON. By using Vega-Lite, we benefit from:
    • A wide range of chart types and composite views (layering, facets).
    • Built-in support for selections, tooltips, zooming, etc., with simple specifications.
    • The ability to compile Vega-Lite specs to Vega or directly render in the browser using libraries like vega-embed.

    The visualization module will translate the chosen chart type and data into a Vega-Lite specification. For example, if the result is a time series of daily transaction counts, we produce a spec:

    json
Copy
{
  "$schema": "https://vega.github.io/schema/vega-lite/v5.json",
  "data": { "values": [ /* result data as array of objects */ ] },
  "mark": "line",
  "encoding": {
    "x": {"field": "date", "type": "temporal", "title": "Date"},
    "y": {"field": "tx_count", "type": "quantitative", "title": "Transactions"}
  },
  "width": "container",
  "height": 300
}

    This JSON tells Vega-Lite to draw a line chart of tx_count over time on the x-axis. We set width to "container" so it responsively fills the parent element. Similar templates are used for bar charts, etc. We can maintain a library of template specs for each chart type and just plug in the field names from the data. In more complex cases, we might need to transform data (e.g. compute percentages for a pie chart). Vega-Lite can do transformations in the spec (like aggregating, binning for histograms, calculating new fields) – we will use those features as needed rather than modifying data in code.

    Vega-Lite is a good choice also because it’s text-based – potentially, the LLM itself could output a Vega-Lite spec if we asked it. However, generating the spec programmatically is straightforward once we know the chart type and data fields, so we don’t need to burden the LLM with detailed chart syntax.

  • Interactivity and User Controls: We want the charts to be interactive:
    • Tooltips: Vega-Lite by default shows tooltips on hover with the data values. We will ensure this is enabled so that when a user hovers on a line or bar, they see the exact values.
    • Zoom/Pan: For time series, enabling zooming and panning can be useful to examine a specific range. Vega-Lite allows defining a selection that is bound to scales – we can enable a drag zoom on the x-axis.
    • Filtering: If a chart has multiple categories (e.g. multiple lines for different tokens), we can add an interactive legend or filter widgets (like checkboxes to show/hide series). Vega-Lite can do interactive selection filtering. Alternatively, we can provide UI controls outside the chart (like multi-select dropdown) that triggers re-rendering the spec with filtered data.
    • Layout Design: The front-end will place the chart in a card-like container, possibly alongside the query text or description. We ensure the layout is responsive using CSS – on wide screens, maybe multiple charts can sit side by side if the user has created several; on mobile, they stack vertically. Vega-Lite charts are responsive if we use relative sizing.
    • We also keep in mind theming – using Solana’s brand colors or a dark theme background if the app supports dark mode. Vega-Lite specs can include a custom color scheme or we can override via CSS on the chart container.
  • Export Features: Users will likely want to export the visualization. We provide multiple options:
    • Download as Image: Using Vega’s ability to export, or the canvas API, we let users save the chart as a PNG or SVG. Vega-Embed library actually provides an option to download PNG/SVG of the chart via a built-in button if enabled.
    • Export Data: Users can download the underlying data as CSV. This is straightforward since we already have the data in JSON – we can offer a “Download data” link.
    • Embed Code: We also allow users to get an embed snippet. For example, an HTML snippet that includes a <script src="https://cdn.jsdelivr.net/npm/vega-embed"> and a container with the Vega-Lite spec JSON. This would let them embed the interactive chart on another web page. However, not all platforms allow arbitrary script embeds.

    To specifically support Notion or Medium:

    • Notion: Notion allows embedding iframes or certain content. We could host the chart on a minimal page (at a shareable URL) and then the user can use Notion’s embed block with that URL. Alternatively, export an image and simply paste into Notion (loses interactivity though). A more advanced idea: Notion has an API; we could potentially push a screenshot into a Notion page if the user connects their account.
    • Medium: Medium does not allow custom scripts or iframes from unrecognized sources for security. The likely route is to use an image. We will allow the user to download a high-quality image of the chart which they can upload to Medium. We might also generate a brief description or alt-text for the image (the LLM can help describe the chart) to accompany it.
  • Responsive Behavior: Ensuring the charts and dashboard as a whole look good on various devices:
    • We rely on Vega-Lite’s responsive width (using container/bounded size) so charts resize to their parent div.
    • The UI will possibly use a fluid grid. If a user has multiple charts in one dashboard, we can implement a drag-and-drop grid layout (using a library like Gridstack or just CSS grid with reposition). But static positioning might suffice if we simply stack charts vertically in the order they were created or allow simple side-by-side for two charts.
    • The text (titles, axis labels) should scale or wrap on small screens. Vega-Lite provides some control (like label angle, skipping labels if too crowded). We might fine-tune the spec for small widths (e.g. rotate x-axis labels 45° if long dates).

In essence, the visualization layer tries to mimic a data analyst’s choice of chart. By automating this, we provide users immediate insight without requiring them to manually pick chart types. And by using a declarative tool like Vega-Lite, we make it easier to maintain and extend the charting capabilities (for example, adding a new chart type like a heatmap later if a query returns matrix-like data).

Saving and Sharing Dashboards

A key feature of SolViz Studio is allowing users to save their charts and even compile them into shareable dashboards. We outline how users can preserve their work and embed it elsewhere:

  • Saving a Chart: When a user creates a visualization (from a query), they can click “Save”. This triggers the backend to store the chart configuration in a database (or a static JSON file if simplicity is preferred). The chart configuration includes:
    • The natural language query the user asked (for reference).
    • The chosen provider and query that was run (for transparency and reproducibility).
    • The result data or a reference to it. We have to decide whether to store the actual data or not. For smaller result sets, storing the JSON data along with the chart spec is fine (ensures the snapshot doesn’t change). For large results, we might re-run the query on load – but that could lead to different data later. Likely we cache the essential data at save time.
    • The Vega-Lite spec or the parameters needed to regenerate it.
    • Metadata like chart title, description (the user might add a custom title/comment before saving).

    Each saved chart gets a unique ID (and perhaps a slug). We expose a URL like /chart/<id> that anyone can use to view the chart. That page would fetch the saved config and render the chart.

  • Dashboards (Multiple Charts): Users should be able to arrange multiple saved charts into a dashboard view. A dashboard could simply be a collection of chart IDs with an arrangement. For a first version, we might skip complex layout and just list charts vertically. Later, we can allow a grid layout customization. The static dashboard generation means we can actually produce a single HTML page that contains all the charts and their data, so that it can be easily shared (similar to how Dune or Flipside share links to dashboards).

    For example, after creating 3 charts, a user creates a dashboard, adds those charts, and clicks “Publish Dashboard”. We then either:

    • Generate a static HTML file that includes Vega embed and the chart specs (which could be hosted on IPFS or our servers), or
    • Provide a dynamic route on our app (like /dashboard/<id>) that loads the charts from the DB. The static approach is interesting because it could be then hosted anywhere (even the user could take the HTML and host themselves).

    Given the user’s request, “static dashboard generation” likely implies the dashboard can be viewed by others without needing them to log in or run queries – essentially a snapshot.

  • Sharing and Embedding:
    • We will support a shareable link for any saved chart or dashboard. Anyone with the link can view the visualization (read-only). This encourages users to share their findings on social media or in articles.
    • For embedding in Notion: Notion’s embed block might allow embedding our shareable link. We should ensure our pages use https and have the appropriate headers to allow iframing. If Notion blocks it, the fallback is inserting an image or GIF.
    • For Medium: as noted, an image is the likely format. We might add a one-click “Export to Medium” which simply downloads the image and copies a caption to clipboard (the user still manually inserts it into a Medium story).
  • Versioning and Updates: If the underlying data changes and users want an auto-updating dashboard (like always show last 7 days data updated daily), we could integrate that by re-running queries on a schedule. However, this complicates the “static” nature. Possibly we offer two modes: snapshot vs live. A snapshot dashboard doesn’t change (data is frozen at save time). A live dashboard would re-run queries whenever opened – but that requires using API credits each time. Given many users will prefer consistency when sharing analysis (so others see the same numbers they saw), we default to snapshotting data. Advanced users might refresh a chart manually and save a new version.
  • Real-world Integration Patterns: We take inspiration from existing platforms:
    • Dune: Users create dashboards composed of visualizations from queries. We mimic this by allowing multiple charts on a page, and like Dune we provide a share link. We can cite that Dune’s model is to let people fork dashboards or queries; we might implement a “Clone chart” feature to let someone else use a saved chart as a starting point.
    • Flipside Studio: Flipside has a concept of collections and dashboards where each chart is tied to a querymedium.commedium.com. They let users publish dashboards with auto-updates. We will likely keep it simpler (manual save) at first.
    • Notion integration: Some tools provide embedded iframes with live charts (e.g., an ObservableHQ notebook or a Data Studio report can be embedded). If we host a public page for the chart, a Notion user can embed it by just pasting the link (Notion will create an embed frame if it recognizes the content). We’ll test this and document for users.

In summary, SolViz Studio will not only allow interactive query and visualization in-app, but also make it easy to preserve and disseminate insights. By generating standalone visualizations and dashboards, it empowers users to use Solana data insights in blogs, reports, or social media. The combination of an LLM for query generation, multiple Solana data sources for comprehensive coverage, and Vega-Lite for polished visuals results in a powerful tool for the community to explore and share Solana on-chain data.

Best Practices and Future Considerations: Throughout the design, we’ve incorporated best practices from real-world examples – using streaming APIs for low-latency needshelius.dev, SQL warehouses for heavy analyticshelius.dev, structuring LLM outputs with function calls for reliability, and caching schema info for the modeluber.com. The Solana ChatGPT plugin provided a reference for multi-source integration (it combined RPC, HelloMoon, and Hyperspace APIs to answer questions)github.comgithub.com, which validated our approach of switching providers per query type. As we implement SolViz Studio, we will continuously refine the prompts (possibly fine-tune on Solana-specific query examples) and expand our library of chart templates. With these in place, the end result will be a comprehensive, user-friendly platform for Solana analytics: ask a question, get the answer visualized – and share it with a click.
